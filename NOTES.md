## Шаг 2 — хуки (29.09.2026)

- **Один вход** `hooks/scripts/dispatch.mjs <Event>` на пять событий: `SessionStart`, `UserPromptExpansion`, `PreToolUse` (все инструменты: §9 требует журналировать каждый вызов), `PostToolUse` (запись файлов), `SubagentStop`. Только Node, без зависимостей; контракт берётся из `lib/crew-contract.mjs`. Цена: ~20 мс на вызов инструмента вне crew-сессий и ~33 мс внутри.
- **Отличия от PLAN.md:**
  - команда в shell-форме (`node "${CLAUDE_PLUGIN_ROOT}/…"`), а не exec-форма — проверена на живом CLI;
  - метка сессии — `.crew/sessions/<id>.json`, как в контракте (шаг 1);
  - `WebFetch` не ограничен allowlist'ом: §9 требует этого только для `curl`/`wget`, а агентам нужна документация. Вызовы `WebFetch` журналируются.
- **Только в crew-сессиях** (решение 6). `/agent-crew:new-project` и `/agent-crew:feature` через `UserPromptExpansion` пишут метку `.crew/sessions/<session_id>.json` и `.crew/.gitignore` (`logs/`, `sessions/`). Хост (eval-раннер) вместо метки задаёт `CREW_HOST`. В остальных сессиях хук выходит сразу и ничего не пишет. `/status` сессию не помечает: он только читает.
- **Политика** — `hooks/policy.core.json` плюс `skills/stacks/<профиль>/policy.json` поверх. Там защищённые ветки, разрешённые хосты, пороги для пакетов и их allowlist, зоны записи по ролям, безопасные команды и цены.
- **Три исхода `PreToolUse`:**
  - `deny` с причиной для агента («Blocked by the agent-crew policy: …»);
  - `allow` — для записи в своей зоне и для цепочек из безопасных команд;
  - без ответа — решает хост по режиму прав пользователя.
- **Что запрещено (§9):**
  - `rm`/`find -delete` вне проекта, всего проекта или с целью, которую нельзя вычислить заранее;
  - запись вне проекта: редиректы, `cp`/`mv`/`install`/`ln`/`tee`/`touch`/`mkdir`/`truncate`/`dd of=`/`sed -i`;
  - `git push` в main/master, force-push (`-f`, `--force-with-lease`, `+refspec`), `--all`/`--mirror`;
  - `curl`/`wget` на хосты не из списка;
  - установка и запуск через npx/dlx пакетов не из allowlist, которые не прошли проверку реестра (существует, старше 30 дней, от 1000 скачиваний в неделю); git-, URL-, file-спецификации, свои реестры и глобальные установки;
  - настоящие секреты в `.env*` (шаблоны `.env.example` и локальные значения docker compose разрешены) и любая запись в `.env` через shell;
  - запись вне зоны роли.
- **Как разбирается shell:** разбор best-effort. Он раскрывает `sudo`, `env`, `sh -c`, `eval`, `xargs`, `find -exec` и `$(…)`, отслеживает `cd`. Переменные и подстановки считаются неизвестными: для опасных команд это запрет, для остальных — просто без автоодобрения. Скрипт из `sh -c "…$X…"` проверяется по именам команд, но автоодобрения не получает никогда.
- **Проверка реестра:** кэш в `${CLAUDE_PLUGIN_DATA}/registry-cache.json` (успех — сутки, отказ — час). Сетевые ошибки дают отказ и не кэшируются.
- **`PostToolUse`:**
  - файл в `.crew/`, нарушающий контракт, возвращает `decision: block` со списком ошибок и подсказкой про `crew` CLI;
  - правки кода пишутся в `.crew/logs/edits.jsonl` как хэши «до/после» (для поиска метаний на шаге 3).
- **`SubagentStop`** добавляет в `.crew/costs.log` оценку (`source: estimate`) по транскрипту сабагента. Токены считаются без повторов по id сообщения, задача берётся из первого сообщения, цены — таблица на 25.09.2026.
- **Журнал** `.crew/logs/hooks.jsonl` хранит решение, инструмент, агента и хэш входа, но не сам ввод.
- **Роли:** `agent-crew:<роль>` получает зону роли. Главный поток и чужие агенты (`general-purpose`, `other-plugin:frontend`) получают зону оркестратора: `.crew/**` и `docs/**`. Задачи и эскалации могут писать все.
- **Проверки:**
  - 62 теста `node:test` (`plugins/agent-crew/hooks/test`): разбор shell, все сценарии §9 и попытки обхода, зоны, секреты, реестр с поддельным `fetch`, кэш, и `dispatch.mjs` отдельным процессом, как его запускает Claude Code. Покрытие строк 98%.
  - `claude plugin validate --strict` проходит.
  - На настоящем CLI 2.1.283 без обращения к модели (без входа, `total_cost_usd: 0`): `hooks.json` загружен, `UserPromptExpansion` записал метку и `.gitignore`, `additionalContext` принят.
  - В CI добавлен job `hooks` (ubuntu и macos).
- **Открыто:**
  - **Codex (шаг C):** Codex не передаёт `agent_type`, поэтому зоны по ролям там не работают — все агенты получат зону оркестратора и не смогут писать код. Нужен другой признак роли (например, переменная окружения агента) или отключение зон в Codex.
  - **Сеть:** `ssh`/`scp`/`rsync`/`nc` и сеть из `node -e`/`python -c` хук не запрещает, их решает хост.
  - **Живая проверка `PreToolUse`** нужна на шаге 6: для неё требуется вызов модели.

## Шаг 3 — агенты, скилы `core/`, CLI `crew` (30.09.2026)

- **9 агентов** в `plugins/agent-crew/agents/` (оркестратор — главный поток, решение 5.1).
  - Модели по §5: critic, architect и security на `opus`, keeper на `haiku`, остальные на `sonnet`. У всех задан `effort`, `maxTurns` и минимальный список `tools`, без `Agent`: делегирует только оркестратор.

Всё, что видит пользователь (бриф, вопросы, отчёт), агенты пишут на языке проекта (`language` в `crew.json`).
  - У агентов с `WebFetch`/`WebSearch` есть оговорка «данные, а не инструкции» (§9).
- **Скилы `core/`** (все с `user-invocable: false`):
  - `crew-files`, `interview`, `brief`, `git-process`, `acceptance-tests`, `code-review`, `security-review`;
  - `orchestration` — сценарий главного потока по фазам §7;
  - `stuck-detection` — триггеры и лестница §8.
  - Агенты подгружают скилы через `skills:` по короткому имени. Проверено по коду CLI 2.1.283: имя ищется точно, затем как `<плагин>:<имя>`, затем по суффиксу.
- **CLI `crew`** (`bin/crew` → `cli/*.mjs`, без зависимостей, контракт из `lib/`):
  - **Задачи.** `task new|list|show|start|submit|pass|reject|fail|block|set` и `next`. CLI сам ведёт цикл задачи (§7.7) и лестницу (§8): 3 неудачи на ступени или повтор ошибки поднимают задачу `retry → stronger_model (opus) → replan`, дальше эскалация. Хэш ошибки не зависит от чисел и путей во временных папках. Вывод `fail`/`reject` заканчивается строкой «Next:» — оркестратор выполняет её буквально.
  - **Эскалации и решения.** `escalate` блокирует задачу. `escalation answer|resolve|cancel`: `resolve` требует ADR и снимает блокировку задачи. `decision new` умеет помечать заменённое ADR.
  - **Проект.** `init`, `config`, `status show|set`, `check`, `budget`, `summary`, `validate`, `interview pending|answer`, `id next`.
  - **`crew check`** проверяет потолок бюджета (по отчёту хоста, иначе по оценке), долю бюджета задачи, взаимные откаты правок (по `logs/edits.jsonl`) и эскалации, на которые пора ответить.
  - Id выделяются эксклюзивно; запись атомарная; перед созданием файла данные проверяются схемой, поэтому пустых файлов после ошибки не остаётся.
- **Контракт** (версия остаётся 1, добавлены только необязательные поля): `ladder` у задачи, `language` в `crew.json`, папка `.crew/reviews/`. Написан `crew-contract/README.md` (PLAN §2.5).
- **Хуки:**
  - команды переведены в exec-форму (`command: node`, `args`), как рекомендуют документация и PLAN;
  - `SubagentStart` передаёт каждому агенту плагина контекст: стек и скил `<стек>-stack`, язык проекта, автономию, правила `.crew/`, оговорку про веб-контент;
  - метка сессии хранит снимок конфига: переменные `CLAUDE_PLUGIN_OPTION_*` могут не доходить до Bash, а CLI должен видеть тот же потолок бюджета;
  - `SubagentStop` обновляет `spent_usd_estimate` задачи;
  - **роли `crew`-команд** (`crewCommands` в политике): `task pass|reject --stage X` может запустить только агент X, `task set`, `init`, `escalation answer|resolve` — только оркестратор, `decision new` — архитектор и оркестратор, `status set` — хранитель и оркестратор;
  - **поля задач и эскалаций** нельзя менять через Write/Edit: хук сравнивает frontmatter до и после, текст ниже frontmatter править можно; новые файлы создаёт только CLI;
  - **git в общей рабочей копии:** всем запрещены `stash`, `reset --hard`, `clean`, `restore`, `checkout` файлов, `commit --amend` и `--no-verify`, `rebase`. Переключать ветки и делать `git add -A` / `commit -a` может только оркестратор. `git stash`, `checkout`, `merge` и `restore` убраны из списка безопасных команд, добавлен `npm audit`;

## Шаг 4 — шаблон и скилы `stacks/tanstack/` (30.09.2026)

- **Шаблон `templates/tanstack/`** собран по выводу официального генератора (`@tanstack/cli create` с дополнениями drizzle и eslint), а не по памяти. Версии на 30.09.2026: TanStack Start 1.168, Router 1.170, React 19.3, Vite 8.3, Drizzle 0.45 + `pg`, Tailwind 4.3, Zod 4.6, Vitest 5, Playwright 1.63, TypeScript 6.0. Генератор тоже ставит TS 6, хотя TS 7 уже вышел. `package-lock.json` закреплён ради воспроизводимых установок: в нём есть нативные модули для Linux, macOS и Windows.
- **Что есть в шаблоне:**
  - вход по email и паролю, собственная реализация без зависимостей (почему — ниже):
    - пароли — scrypt из `node:crypto`;
    - сессии хранятся в БД (в базе только SHA-256 токена), cookie httpOnly/SameSite=Lax;
    - роли `owner`/`staff`, `requireUser(...roles)` для серверных функций;
    - вход с возвратом на исходную страницу и защитой от открытого редиректа;
  - защищённый раздел `_app/`;
  - UI-блоки с подписями и ролями (`Field`, `Button`, `Alert`);
  - строки интерфейса в `src/lib/text.ts`, чтобы переводить экраны на язык проекта;
  - PostgreSQL 17 в Docker Compose (порт настраивается через `DB_PORT`), первая миграция и идемпотентный seed владельца;
  - 5 unit- и 4 e2e-теста;
  - проектный `CLAUDE.md` с правилами для всех агентов и README для человека.
- **Своя аутентификация, а не Better Auth из генератора:**
  - Better Auth требует секрета и настройки адаптера;
  - его серверные вызовы через cookie-плагин могут переключить сессию: владелец, создавая аккаунт сотрудника, рискует оказаться залогинен под ним;
  - маленький модуль агенты прочитают целиком.
  Из allowlist убраны `better-auth` и `argon2`, чтобы у проекта был один способ входа.
- **Что узнали о текущем TanStack Start:**
  - `createServerFn().inputValidator()` уже устарел, нужен `.validator()`, хотя генератор пишет старое имя;
  - Zod-схема принимается прямо в `.validator()` и `validateSearch`;
  - есть встроенная защита импортов: файлы `*.server.*` и `@tanstack/react-start/server` запрещены в клиентском коде. На этом держится раскладка «хелперы в `*.server.ts`, серверные функции в `src/server/*.ts`». Проверено: в клиентском бандле нет ни `pg`, ни scrypt;
  - Vite 8 сам понимает пути из `tsconfig`;
  - `noUncheckedIndexedAccess` включён: без него правило линтера `no-unnecessary-condition` ругается на естественный код `const [row] = …; if (!row)`.
- **8 скилов профиля** (по §10):
  - `tanstack-stack` — точка входа: настройка проекта, команды, раскладка и владельцы, какой скил когда грузить;
  - `-routes`, `-drizzle`, `-auth`, `-forms`, `-tables`, `-reports`, `-e2e`.

  Скилы привязаны к путям через `paths`. Все примеры в них сначала написаны и проверены в пробном модуле «клиенты»:
  - список с поиском и страницами, формы с ошибками полей;
  - дубль телефона: ошибка БД — `DrizzleQueryError` с `cause.code === '23505'`;
  - удаление только владельцем и с подтверждением;

## Изменения по требованиям пользователя (01.10.2026)

- **Потолок расходов больше не ставится по умолчанию.** `budget_cap_usd` по умолчанию 0 — «без потолка»: на подписке действуют лимиты плана, и считать доллары незачем.
  - Claude Code не сообщает плагину способ оплаты сессии, а модель называет только в событии `SessionStart`. Поэтому «платную» сессию хуки определяют по косвенным признакам: `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`, переменные облачных провайдеров или модель из списка `payPerUse.models` в `policy.core.json` (сейчас — Fable).
  - В такой сессии без потолка оркестратор один раз говорит человеку, что лимита нет и где его задать. Диалог настройки показать условно нельзя: `userConfig` не умеет зависеть от модели.
  - Модель сессии хук `SessionStart` запоминает в `${CLAUDE_PLUGIN_DATA}/session-models.json` (последние 40 сессий) — единственное, что плагин пишет вне crew-сессий.
- **Стек больше не фиксирован** (`stack_profile=auto` по умолчанию, `tanstack` остался пресетом).
  - Новый скил `core/stack-rules`: архитектор выбирает стек под бриф (или определяет по существующему коду), создаёт каркас штатным генератором, пишет правила в `.crew/stack/` — индекс и по файлу на технологию, по официальной документации установленной версии — и политику `.crew/policy.json`.
  - Хуки накладывают политику проекта поверх базовой. Она может только добавлять: зоны записи для frontend/backend/db/qa/architect (не `.crew/`, не `.git/`, не «весь проект»), безопасные команды из словаря инструментов сборки и тестов (с подкомандой), пакеты. Защищённые ветки, секреты, сеть и запреты базовой политики ей недоступны. Негодные записи отбрасываются, а архитектор сразу получает их список (PostToolUse).
  - Профиль для политики берётся из `crew.json` проекта, а не из настроек сессии: проект, начатый на пресете, остаётся на нём.
  - Агенты читают правила по указанию хука `SubagentStart`: `.crew/stack/README.md`, либо скил пресета, либо «стек ещё не настроен».
  - `crew scaffold` для `auto` отказывается с подсказкой; `/feature` больше не требует стек tanstack.
  - Eval-раннер по-прежнему строит на пресете (`CREW_STACK_PROFILE`), чтобы оба режима стартовали с одного шаблона.
- **Без Docker по умолчанию** (0.2.2): в режиме `auto` архитектор обязан выбрать встроенную файловую базу данных; сервер базы — только по требованию брифа или владельца. Docker остался нужен лишь пресету `tanstack`.
- **Три улучшения по итогам сравнения с Superpowers, GSD, BMAD, gstack и Compound Engineering** (плагин 0.3.0, расширение 0.3.1):
  - `/agent-crew:continue` — продолжить прогон в любом чате, в том числе новом. Команда создаёт маркер crew-сессии, поэтому хуки включаются и в свежей сессии; обычная фраза «продолжай» в новом чате оставила бы прогон без них. Скил `orchestration` на границах фаз предлагает человеку свежий чат. Расширение шлёт эту команду вместо текста.
  - `/agent-crew:fix` — короткий путь: тест, показывающий проблему (QA), исправление (владелец кода), одна проверка. Без интервью, брифа и архитектуры.
  - Настройки `model_tier` (`economy` / `balanced` / `quality`) и `review_depth` (`every-task` / `qa-only` / `final-only`). Уровень моделей оркестратор применяет параметром `model` при вызове агента: в заголовке агента подстановка настроек не работает. Глубину проверок применяет CLI: при `qa-only` задача закрывается после QA, при `final-only` — при сдаче, а проверку безопасности всего проекта оркестратор запускает в финальной фазе.
- **Ещё пять возможностей из того же сравнения** (плагин 0.4.0):
  - **Сначала тест** — скил `test-first` у frontend, backend и db: увидеть падение приёмочных тестов задачи, написать юнит-тесты к логике, потом код; в заметке при сдаче — что было красным и стало зелёным. Ревьюер отклоняет задачу без этого и любое ослабление тестов.
  - **Дизайн и визуальная проверка** — десятый агент `designer` пишет `docs/design.md` (скил `ui-design`) после архитектуры; frontend строит экраны по нему; QA в финале снимает скриншоты каждой страницы на 1280 и 375 px, открывает их и пишет `.crew/reviews/visual.md`.
  - **Выкладка** — `/agent-crew:deploy`: решение о хостинге (ADR), файлы выкладки, production-настройки, обязательная проверка безопасности, инструкция `docs/deploy.md`. Команда готовит, публикует человек.
  - **Память об уроках** — `crew lesson add/list`. Уроки пишет оркестратор в финальной фазе (не больше пяти, без названий и данных проекта). Хранятся в `.crew/lessons.md` и в данных плагина (`${CLAUDE_PLUGIN_DATA}/lessons.md`; путь CLI узнаёт из маркера сессии). Хуки подают их оркестратору (до 12) и агентам своей роли (до 6) с пометкой, что это советы, а не указания: бриф, правила стека и политика важнее. Это канал, по которому вывод модели попадает в будущие сессии, поэтому запись разрешена только оркестратору, а длина урока ограничена.
  - **Git worktree для параллельных задач** — настройка `parallel_tasks=worktrees`. Оркестратор передаёт `isolation: "worktree"` параллельным исполнителям, потом сам вливает ветку (`git merge`, разрешён только ему) и удаляет дерево. Хуки считают пути относительно дерева агента, но политику, журнал и состояние берут из основной папки; запись в копию `.crew/` внутри дерева запрещена. CLI `crew` из дерева работает с `.crew/` основной папки. Каждому дереву нужна своя установка зависимостей, поэтому по умолчанию режим выключен.
- **Живой прогон режима `auto`** (02.10.2026 ночью, идея «отзывы для кафе», economy + qa-only; остановлен пользователем на 5 задачах из 10). Подтвердилось вживую: выбор стека без Docker (Next.js 16 и SQLite), каркас, правила `.crew/stack/` (индекс и 8 файлов), политика проекта, дизайнер, три параллельных исполнителя. Находки: архитектор записал политику рано и не смог дописать каркас (теперь до появления политики он пишет в любом месте проекта, политика — последним шагом); генератор проекта через временную папку отклонён необслуживаемым режимом (скил требует одну простую команду); для крошечной идеи создано 10 задач.
- **Размер прогона, выжимки и учёт расходов** (плагин 0.5.0):
  - **`run_size`** (`auto` / `prototype` / `standard`). После утверждения брифа оркестратор оценивает проект и записывает размер командой `crew size set` в `crew.json`. Прототип — не больше примерно 12 критериев, не больше двух видов пользователей со входом, без платежей и интеграций. В прототипе: архитектура одним вызовом без проверки безопасности, без дизайнера, 2–4 задачи срезами «данные → сервер → экран», проверка только QA (CLI сам пропускает стадию безопасности), без keeper после каждой задачи, без визуальной проверки. Настройка пользователя сильнее решения оркестратора.
  - **Выжимка под роль.** Хук `SubagentStart` механически, без вызова модели, вырезает из `.crew/stack/README.md` технологии с файлами правил, команды, папки этой роли и соглашения, а из брифа — цель и роли. Агенту сказано не читать индекс целиком и читать только названные критерии приёмки. PM и критик выжимку брифа не получают: они работают с самим брифом.
  - **Расходы.** `crew budget` показывал последнюю сумму от хоста и игнорировал всё, что случилось после неё; отчёт, написанный в финальном вызове, занижал расход ($5.54 вместо $10.45 в первом полном прогоне). Теперь к сумме хоста добавляются оценки по агентам, отработавшим после последнего отчёта, и строка прямо говорит, что текущая сессия посчитана не полностью.
- **Удобство** (плагин 0.6.0, расширение 0.3.2):
  - **Постоянное разрешение.** Настройка `approvals` (`ask-first-time` / `auto` / `manual`). По умолчанию оркестратор в первом прогоне задаёт один вопрос через AskUserQuestion с заголовком «Crew access» и тремя вариантами: всегда, только в этом проекте, спрашивать каждый раз. Ответ записывает хук `PostToolUse` в данные плагина (`consent.json`), а не модель: агент не может выдать разрешение сам себе, а склонированный репозиторий не может принести его с собой. При согласии хук `PreToolUse` отвечает `allow` на всё, против чего политика не возражает. Запреты политики остаются; инструменты MCP и чужих плагинов и shell-команды, которые политика не смогла прочитать, по-прежнему спрашивает Claude Code. Снять разрешение: `crew approvals reset`.
  - **Строка состояния субагентов** — `settings.json` плагина задаёт `subagentStatusLine`, скрипт `scripts/subagent-status.mjs` выводит для агентов команды «роль · задача · состояние · токены · время». Работает ли подстановка `${CLAUDE_PLUGIN_ROOT}` в этой настройке, документация не говорит; проверено только на тестовых данных.
  - **Расширение:** команды Fix и Prepare Deployment.
  - **Журнал изменений плагина** — `plugins/agent-crew/CHANGELOG.md`, теги `plugin-vX.Y.Z`.
- **Не проверено с моделью:** прототип, выжимки, уроки, визуальная проверка, `fix`, `deploy`, worktree, постоянное разрешение и строка состояния.
